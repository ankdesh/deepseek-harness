# Agent Note: 按产品选择包的发行方式

Status: proposed

[English](2026-10-29-selected-product-packages.md) | 中文
## 问题

通过源码链接运行的应用依赖完整的 Harness 源码检出。完整的启动器和 UI bundle 还会安装应用未启用的功能。较短的直接依赖列表不能衡量最终安装内容。

## 提案

通过 GitHub Packages，在下游账户作用域下发布选定的构建产物包。保留常规配置启动器。将 Web 启动与 UI 选择分离，并提供不依赖源码仓库的配置准备和组装工具。保留现有模型适配器。使用方清单显式声明其服务和 UI 模块。

发行归档包含精确版本、源码和使用方提交、校验和以及每个配置的包清单。通过临时注册表和真实的使用方依赖根验证同一批归档。使用候选安装运行使用方要求的验收测试配置。发布流程检查完整证据，发布这些字节，验证注册表完整性，并且仅在所有包均可用后创建升级元数据。

## 已考虑的替代方案

仅修复依赖声明仍会保留完整 bundle。单个编译后的应用包可以减少可见包名，但会增加原生文件、动态模块、调试和各应用独立选择的复杂度。保留独立模块允许后续产品选择其他能力。

## 验收条件

干净的 Web 和无界面使用方无需检出 Harness 源码即可安装、构建和启动。无界面配置不包含浏览器 UI 包。功能和历史记录保留所需行为。完整安装集的测量包含第三方包。缺失凭据、检查失败、输入有未提交更改或发布不完整时，禁止升级。源码链接仅作为显式开发模式保留。

## 风险

保留的模型适配器仍引入较多第三方代码。作用域改写必须覆盖构建后的导入、类型、配置和原生载荷引用。必需的真实模型检查需要 CI 凭据。即使安装成功，现有应用回归仍可能阻止发行。公开发布和其他平台需要单独审查及测试。
